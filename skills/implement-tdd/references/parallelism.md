# Waves — cycles side by side

Read by the `run-lot` design. The workflow runs one `tdd-cycle` agent per cycle, its RED then its GREEN. A cycle starts once every earlier cycle it **meets** is done, `run.parallelCycles` of `kit.config.json` at most side by side (2 by default, 3 at most). Two cycles meet when one writes a file the other writes (`files` of `--index`: `full`, `toCreate`, `production`, `ripple`), or when a later wave reads `bounded` (`bounded`, `boundedGreen`) a file an earlier wave writes; a cycle without code files meets every other. There is no barrier between waves: `wave` orders the cycles, the files decide who waits.

- **Same wave** = cycles whose tests touch neither the same test file nor the same production code — typically one Application + one Infrastructure or WebAPI. Check on the sheet: shared fixture, shared builder under `layout.tests.shared`, or one test class carrying both scenarios → successive waves. `cctoolkit sheet-cycles <sheet> --index` refuses two cycles of one wave sharing a `full` test file or a `production` file.
- **One test file per behaviour.** Two cycles rewriting one test class always run one after the other. Where the layer allows it, give each behaviour its own test class (one per use case, or one partial class per behaviour), so that only a production file both write keeps them apart.
- **What a later cycle uses goes under `bounded`.** A cycle whose tests or code use a type, member or file an earlier cycle creates names that file in `bounded` (or `boundedGreen`): that is what makes it wait for the earlier cycle. Left out, the two may run side by side and the later one fails to compile.
- **Shared registry → declaratives.** Cycles that each add an entry to one file (error code, catalogue entry, enum member) would follow one another: list every entry in `declaratives`, the run writes them before the first RED, and drop the file from those cycles' `production`. `--index` refuses a production file in more than 3 cycles.
- **A signature stub** a RED needs in a file another cycle's GREEN fills → that cycle names the file in `bounded` and goes one wave later.

**One cycle = one homogeneous pattern, one test project, at most 4 test files rewritten and 8 production files.** Every RED and every GREEN costs a fixed spawn, build and read; eleven small cycles for one repeated change cost three times four grouped ones. Group what the same reasoning settles — the same change applied to several exceptions, handlers or endpoints — into one cycle, as long as one test project carries it and the caps hold; `cctoolkit sheet-cycles <sheet> --index` enforces them (test files under `layout.tests.shared` of `kit.config.json` excepted). Past a cap, split by test class or by production folder, each sub-cycle carrying the same step title and its own methods. Sub-cycles never share a test method: a data-driven theory (one row per route, per case) splits into one theory per sub-cycle — the runner filters a method, never a row, so the rows another sub-cycle adds keep this one's GREEN red. `--index` refuses a method in two cycles, whatever their waves. A sub-cycle with no production of its own (its tests only observe what another sub-cycle's GREEN writes) is not a cycle: keep its tests in the cycle that drives that code.

**A `file in use` / locked-output build error in an agent = build collision**, not a design fault: two agents building the same output directory at once. Cycles side by side run their builds under `cctoolkit build-lock`; have the agent re-issue its filtered command, don't re-delegate.

**Turn budget.** `tdd-test-author` stops writing past about 26 turns and reports what it wrote; a cycle with more methods than one agent writes in that budget comes back partial and is retried. Keep a cycle's methods to what one agent writes in a sitting — about a dozen of the same shape, fewer when each needs its own fixture.
