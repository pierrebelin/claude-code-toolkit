# DDD rules

The plan classifies **every id**: `applied` or `N/A — reason`. A batch sheet cites only the applied ids. The verifier rejects an id missing from that coverage.

| ID | Rule | When | Plan decision and evidence | Exception |
|----|-------|-------|----------------------------|-----------|
| DDD-01 | Names come from the business language, never a technical term or a generic service. | Always, when Domain/Application changes. | Name the concept and its owner; code and tests use that vocabulary. | None. |
| DDD-02 | An aggregate is a consistency boundary; it owns its invariants. | A command modifies business state. | Name the aggregate + the RM; a Domain method prevents the invalid state. | Several aggregates only under DDD-08. |
| DDD-03 | Change happens through a business method, never a setter or a mutation from the handler. | Aggregate state is modified. | Name the semantic method; the handler orchestrates without modifying properties. | None. |
| DDD-04 | A Value Object is a valid, immutable concept, equal by value. | Data carrying its own business rule or identity. | Name the concept and the invariant; validation inside the VO. | A primitive type if there is no rule and no proper semantics. |
| DDD-05 | Cross-aggregate references by ID, never object navigation. | One aggregate designates another. | Name the ID and the read need; no collection of foreign aggregates. | None. |
| DDD-06 | `Create()` creates/validates/emits; `Restore()` only rehydrates. | Creation or persistence read. | Name the Create/Restore path; the repository calls only Restore to read. | None. |
| DDD-07 | A domain event is a past fact internal to persistence, with explicit type and payload. | A mutation is persisted through an event. | Name the event in the past tense and its payload; no outbox and no integration event. | N/A if no evented mutation. |
| DDD-08 | A command modifies and saves a single aggregate. | Any write command. | Name the single aggregate modified/saved; an external read stays targeted and non-mutating. | An explicit exception, with its business reason and consistency stated in the plan. |
| DDD-09 | Logic belongs to the object owning the data; a Domain Service only when no business object owns it naturally. | A business operation with no obvious owner, or the temptation of a static service/helper: serializer, parser, factory, mapper, transformation, computation. | Name the owner and the call shape: `context.Serialize()`, `ParsedImportFile.Create(json)` — never `Serializer.Serialize(context)` nor `IParser.Parse(json)`. For a Domain Service: explain why each aggregate is excluded; stateless, business-level, no Infrastructure dependency, never a repository wrapper. | N/A if an aggregate owns it. |
| DDD-10 | The Domain depends on neither HTTP, EF, SQL, DTOs nor Infrastructure. | Domain touched. | Confine technical dependencies to the boundaries; the Domain compiles without them. | None. |
| DDD-11 | Absence is modelled, never a convenience `null`. | Domain or Application exposes a parameter, a property, a command, a query or a return type. | Missing collection → `[]`, non-nullable `IReadOnlyList<T>`, semantics documented on the method ("empty = no filter"). Optional concept → a Null Object (`NoConstraint`), not a nullable field. Nullables from the transport layers (DTO, query parameter) are converted at the WebAPI boundary (`request.GroupIds ?? []`), never propagated further down. | `null` admissible only for a genuinely optional scalar business value (`string? Description`). |
