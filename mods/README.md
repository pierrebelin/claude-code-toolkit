# Mods

Three optional panes drawn inside Claude Code (terminal or desktop Code tab), to see what the kit is doing without asking: where the batch stands, what the spec already holds, what the knowledge base says, how full the context is. Each one is a small plugin served by the `cctoolkit` marketplace, installed on its own — the kit works without them.

## `run-lot-pane` — follow an autonomous batch

A `/cctoolkit:run-lot` batch runs for tens of minutes across a dozen agents. The pane shows it live: phases with their agents, time and tokens, each agent's model and current tool, retries and stalls flagged as they happen, the batch sheet ticking RED → GREEN → COST (or its `## Cycles` block, each cycle done once its `cycle` line in `run/.work.jsonl` says so), an estimated end, then the outcome and the audit verdict; `c` opens the phase of the current step. Opens by itself when a Workflow starts; `/run-lot-pane demo` shows an example.

![run-lot-pane during a run: a question waiting for its answer, phases with their agents, model and effort, time and tokens, a retry and its rejected attempt, a stall warning, the batch sheet's cycles, the notes](../docs/screenshots/demo-running.png)

A `/cctoolkit:run-plan` run opens on the plan: batches with their state, agents, time and tokens, then the supervisor steps between them. `1`-`9` opens a batch in the view above, `p` returns to the plan; `/run-lot-pane demo plan` shows an example. A plan delivered whole — every batch `DONE`, no stop, no `--until` or `--only` — goes through a `Final check` step (every suite run whole once) and a `Merge` step (`merge prepare`, then the `knowledge-merger` agent drafting and staging the merge), and its knowledge-base merge shows under the outcome: staged and not written yet, in amber, with the files it touches, the warnings left and `/cctoolkit:knowledge-merge <plan>` to review and write it; refused, blocked or failed, in red. `/run-lot-pane demo plan merge` shows one.

![run-lot-pane on a run-plan: six batches, one done, one running, one set aside, three waiting on their dependencies, a pause requested, the notes, the supervisor steps](../docs/screenshots/demo-plan-running.png)

![run-lot-pane on a run-plan delivered whole: two batches done, the knowledge-base merge staged under the outcome with the files it touches and a warning, the final check and merge steps](../docs/screenshots/demo-plan-merge.png)

The pane also steers the run through `run/.pane.jsonl`, a file the mod alone writes and the kit's scripts answer in `run/.work.jsonl`. `v` lists what the run decided without you (the `## To validate` entries of the reports, a divergence, a batch set aside, the breaker's stop, the notes taken): keep, reject or amend each one, applied at the next `/run-plan` or `/run-lot` start or at once with `cctoolkit run-validate apply <work file>`. `n` leaves a note every agent of the batch receives at its next tool call, the ones already running included, `g` draws the plan's dependency graph. A question waiting for its answer shows on every view and above the prompt, with the time left before its recommendation applies.

## `knowledge-pane` — browse the knowledge base, see the spec take shape

The business knowledge base under `knowledge.root`, browsed without spending a token of model context: the pane reads the files itself and writes nothing. The home lists the contexts of `INDEX.md` with their counts and summary, the ADRs, the objects still `observed` by level and the last `HISTORY.md` rows, and warns when a merge is prepared or staged (`partial` for a partial merge) or a sync staged, and not written yet, or when the index lags — with the command to run, `cctoolkit knowledge-index`, which the pane never launches. A context opens on its `OVERVIEW.md`, its use cases with their own rules, the cross-cutting rules, the decisions, the ADRs that cite it and its history; an object on its whole text, a use case's own rules, what it applies to, what cites it, its handlers, its `path:line` and its history rows. Every id is a row to press, `b` walks back, `h` goes home, `s` searches by id, title or handler. While the pane is open, a `cctoolkit ask --id` or `--handler` of the session shows the object it asked for. A staged merge lists its objects, `+` new, `~` modified, `−` retired, each opening on the base as it is, the staged text (or the draft) beneath it. `/knowledge-pane [Context|id|words]` opens it; `/knowledge-pane demo` shows the kit example with a staged merge; while it is shown, the pane neither follows `cctoolkit ask` nor checks the index against the files. In Claude Desktop's Code tab, a `◫ Knowledge` button above the prompt opens and closes it, and a context opens on a matrix of its use cases by the rules they apply, observed ones in amber.

![knowledge-pane on the demo base: a staged merge, the Catalog context, an ADR, an observed rule, the last history rows](../docs/screenshots/demo-home.png)

During a `/cctoolkit:business-spec`, the pane switches to the spec: the decisions you answered, the open questions by severity, the use cases, business rules and sections in view, refreshed on every write. A click unfolds a row in place, `b` folds them back, then walks back to the view under the spec; the home lists the spec followed. Opens by itself when the skill starts or a spec is written; `/spec-pane <path>` follows an existing spec, `/spec-pane clear` forgets it. In Claude Desktop's Code tab, the spec state heads it: side by side, a square per open question by severity and per decision kept, changed, without an answer or pending, the question or the answer on hover; the outline gives each part its count; the button above the prompt reads `◫ Spec` while the spec is on top.

![The spec view: open questions by severity, use cases and business rules, one of each unfolded](../docs/screenshots/spec.png)

## `context-band` — know when to `/clear`

A line under the prompt, above it in Claude Desktop's Code tab: context meter, 5h limit, prompt-cache expiry, session time and cost. `▸ details` adds the `/clear` step (150k, ceiling 250k) and what filled the context over the last turns. Always on.

In Claude Desktop's Code tab the three panes draw for the desktop rather than as terminal text: drawn bars instead of block glyphs, a type scale, spacing in place of `│` and `⎿`, real buttons (`Details`, `Back`, `Close`, `Note`…), and the knowledge base's texts as Markdown. In a terminal they read the same way in a fixed face: colour is kept for state (a glyph or a signal, never a name, so `RED`, `GREEN` and the batches stay in the text colour), done in the text colour with a green `✓`, running in bold behind the spinner, to come dimmed; each block opens on a bold title and a dim rule to the pane's edge, a blank line apart, its rows at one column per level and its figures (agents, time, tokens) right-aligned in columns that a label is cut to fit, never the figures; only what waits on you is framed (a run's outcome, a plan stopped, a knowledge-base alert); a long detail is cut with `…`, a wrapped line hangs under its first.

![context-band under the prompt: context meter, 5h limit, cache, /clear step, top contributor](../docs/screenshots/band.png)

## Install

From the repo root, type it yourself — the auto-mode classifier refuses an agent enabling plugins. The marketplace is the kit's own: skip the first line if `cctoolkit` is already installed (`INSTALL.md`).

```bash
claude plugin marketplace add pierrebelin/claude-code-toolkit --scope project
claude plugin install context-band@cctoolkit --scope project
claude plugin install knowledge-pane@cctoolkit --scope project
claude plugin install run-lot-pane@cctoolkit --scope project
```

Take only the ones you want, then restart Claude Code in the repo. Inside a session, `/plugin install <mod>@cctoolkit` does the same.

A repo that installed them from `.claude/mods/` (the former `pierrebelinmods` marketplace): `/cctoolkit:kit-init` removes that marketplace and tells which mods to reinstall.

Check it loaded:
```bash
claude -p "ok" --max-turns 1 --debug --debug-file /tmp/mods.log >/dev/null
grep 'hooks module' /tmp/mods.log   # one "loaded" line per mod
```

## Layout of a mod

```
<mod>/
  .claude-plugin/plugin.json   name, version, description, "types": "./types/index.d.ts"
  hooks/hooks.json             { "modules": ["./register.tsx"] }
  hooks/register.tsx           export const register: Register = on => { ... }
  types/index.d.ts             the $.state contract (interface PluginState)
  tests/*.test.tsx             claude plugin test
  tsconfig.json                extends the engine-laid types
  .gitignore                   .claude-plugin/types/ (laid by the engine)
```

## Writing a new mod

1. Load the `plugin-authoring` skill: it names the session's dev-mods folder and turns hot reload on. Write and iterate there.
2. `claude plugin validate <mod>` and `claude plugin test <mod>` green.
3. Copy it here without the engine-laid types: `rsync -a --exclude .claude-plugin/types/ <dev-mods>/<mod>/ mods/<mod>/`, delete the dev-mods copy (two loaded copies of one name collide), add its row to the toolkit root's `.claude-plugin/marketplace.json` and to `enabledPlugins` of the toolkit's `.claude/settings.json`.
4. `claude plugin validate .` from the toolkit root to check the marketplace.

Traps met with the API: in tests, call hooks (`fs.read`, `store.get`, `ui.open`…) answer `{ value: … }`; the fallback `ui.render` returns a tree (`<Box key="engine" />`), never `null`; `$` is only passed to functions declared at module level; when the state shape changes, merge with the empty value (`{ ...EMPTY, ...stored }`), since `$.state` survives reloads; no toast, no sound.
