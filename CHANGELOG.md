# Changelog

One section per release, newest first, headed `## <version> — <date>`: `cctoolkit` and its mods share one version since 1.6.0, each entry names the plugin it changes. Older sections, headed `## <plugin> <version>`, date from per-plugin versions.

A release that changes a file under `rules/` or `presets/*/rules/` lists it under **Rules changed**, one under `presets/*/skills/` under **Skills changed**: those files are copied into your repo, so you pull them by re-running `/cctoolkit:kit-init`, which shows each difference and asks.

## 2.8.2 — 2026-10-23

2.8.1 was tagged but never released: its CI was red. 2.8.2 carries all of 2.8.1, the notes below it apply.

- `cctoolkit`: `cctoolkit evals` is green on Ubuntu 26 again, whose Rust `coreutils` count `cut -c` in characters where GNU counted bytes. A `pre-audit` case cut a line holding `·` and `—` at 70 and got 3 characters more. The cases now cut with `cut -b`, bytes on both.

## 2.8.1 — 2026-10-23

- `cctoolkit`: the graph autosync (`Stop` hook) finds `graphify` on the PATH. It only tried `~/.local/bin/graphify` unless `GRAPHIFY_BIN` was set, so a `pip` install on Windows (`Python3xx/Scripts`) was skipped on every Stop and the graph never resynced. It now tries `GRAPHIFY_BIN`, then the PATH, then `~/.local/bin`. When none holds it, `/tmp/graphify-hook.log` says `ALERT graphify not found (…)` instead of a silent skip.
- `cctoolkit`: `cctoolkit doctor` checks `graphify` the way the hook resolves it, and names the cause when the graph is behind: `FAIL binary graphify` with what was tried, the `graphify graph` warning pointing at it, and a `graphify autosync` warning when the hook's last run found no `graphify` while your shell does (set `GRAPHIFY_BIN` in the `env` of `.claude/settings.local.json`).

## 2.8.0 — 2026-10-21

- `cctoolkit`: a batch closes `light` unless it touches authorisation, a migration, a public contract or an approved snapshot (the `closing.full` rules of `kit.config.json`). A cycle carrying a signature ripple no longer makes it full, and the presets drop their cap of 12 production files (`closing.maxProductionFiles` is now `0`, no cap; a repo can still set one). The full audit runs on `sonnet` instead of `opus`. On a measured run, the audit phase took about 30 minutes of a 69-minute active batch.
- `cctoolkit`: `run-lot` no longer reviews the next batch's sheet nor amends it. The `adversarial-reviewer` on `opus`, then the agent rewriting the next sheet, ran after every full batch (1 to 5 minutes, two agents). The next batch's own design checks its sheet against the code it finds. `run-plan` no longer sets a batch aside for review questions left without answer, the report loses its `### Next batch review` section, `cctoolkit closing-level` loses `--next` and its `review` / `reviewWhy` fields, and `adversarial-reviewer` loses its `next-batch` mode.
- `cctoolkit`: `cctoolkit pre-audit` no longer starts one `grep` per line of the repo's traceability debt. On a repo with about 970 unbound tests it took 82-90 s per run, and a batch could run it up to three times; it now takes 13-14 s, with the same output.
- `cctoolkit`: the Bash hook reads the tool payload without `jq` when it holds only plain strings, and the `rtk` rewrite leaves without a fork for a command `rtk` never rewrites. Measured on Windows (median of 10, loaded machine): `echo hi` 1.07 s → 0.28 s, `git status` 2.81 s → 1.12 s, `cat README.md` 1.48 s → 0.88 s.
- `run-lot-pane`: a cycle agent of `run-lot` (one agent per cycle since 2.6.0, labelled `RED <id> w<wave> … +GREEN`) shows the stage it is at: `GREEN <id>` once its RED state is written, under a phase titled `RED · GREEN` when the run has no GREEN phase of its own.

## 2.7.0 — 2026-10-21

- `cctoolkit`: a batch `run-plan` sets aside keeps its progress. Until now its saved cycles were deleted and its partial work survived only as a patch: the next run started the batch over from its first cycle, and taking the work back meant fixing the cause, `git apply`, writing the decision into the sheet, then relaunching. The work is now also kept under the git ref `refs/cctoolkit/aside/<plan folder>/FX`, created files included, and the batch's cycles and snapshot stay in the run's work file. The next `run-plan` or `run-lot` on that batch puts the work back first (`cctoolkit batch-baseline resume`, a three-way merge with what was committed since), then resumes from the saved cycles. The files put back count as the batch's, never as files you had modified before it. A file that no longer merges: nothing is written, the batch starts over, and the run report lists it under `## To validate` with the patch. Relaunching is now: fix the cause in the sheet's `decisions` (or answer in the `run-lot-pane` mod), then run `run-plan` again.

## 2.6.0 — 2026-10-21

- `cctoolkit`: a resumed `run-lot` no longer skips the cycles of its batch. The agent that reloads the run state relays the cycle index, and on a measured run it relayed `cycles: []` for a 7-cycle block: the run found nothing to do, went straight to the global green, wrote the GREEN of two cycles there outside TDD, then failed the pre-audit three times on cycles with no state (about 20 min lost). `cctoolkit sheet-cycles --index` now prints `count`, the number of cycles of the block; a copy short of cycles is read again by an agent of its own, and a second short copy stops the batch instead of running it empty.
- `cctoolkit`: a GREEN may fix a test that is wrong, and the audit checks what it changed. Until now test files were locked once the RED was written: a GREEN that met a wrong fixture or a value a shared helper normalises had to stop, an arbiter had to grant the file, and the next attempt started over. On a measured run, one GREEN fought that lock for about 9 minutes and through 3 arbiters. The TDD scope hook no longer refuses the change. It writes one `test-edit` line per test file into the run work file, with the assertion lines removed and added. The new `tdd.assertion` key of `kit.config.json` tells what counts as an assertion line; each preset sets it for its stacks (`Assert.`, `Should(`, `Verify(`, `.Received(` for `clean-architecture`). The `## Mechanical audit` table gains the row `Test | Tests changed after the RED checkpoint`: `gap` when an assertion line was removed or rewritten, which the auditor turns into a finding; `ok` when only setup, fixture or compile lines changed. A GREEN lists each test file it changed with the reason (`testsDiff`), and each one appears under `## To validate`. `tdd-implementer` and `tdd-cycle` may change a test only when it is wrong, and never remove, negate or loosen an assertion of the behaviour.
- `cctoolkit`: `run-lot` no longer waits for anyone and runs one agent per cycle. On a measured batch of 7 cycles, the run took about 68 minutes, and about 45 of them went to its control layers rather than to the work: 28 minutes waiting for answers nobody gave, 9 minutes of arbiters around a locked test, and a pre-audit looping on cycles a resume had skipped. The same kind of batch done by hand took 9 minutes.
  - Every cycle, light or full closing, is one `tdd-cycle` agent: its RED, the checkpoint the TDD scope hook checks on the disk, then its GREEN. Refactor and guard cycles go through it too: `cctoolkit sheet-cycles --cycle <id> --red` marks them with a `Kind:` line, so the checkpoint accepts a RED that passes at once. Cycles of a wave whose files do not meet run in parallel.
  - A rejected cycle gets one retry with the reason, then one last attempt on `opus` with every reason. A RED already accepted, saved by an earlier run or by an attempt whose GREEN was rejected, is re-armed as is, and only the GREEN is written again. A refactor or guard cycle that still fails is left out and listed to validate; any other cycle stops the batch at once, `BLOCKED`.
  - No question, no wait, no arbiter: an ambiguity is decided by the agent that meets it and listed under `## To validate`. A flagged `Cost` line is no longer a rejection: it is listed under `### Reported without fixing` and judged by the audit on the Cost axis. Every answer of the next-batch review is applied and listed, human-only questions included; a Blocking question with neither source nor answer still sets the next batch aside under `run-plan`.
  - The pre-audit gate runs once, and what it leaves red goes to the audit. The audit runs once (light review or full audit), then one fix. A second review follows only a Blocking on Correctness, on the files the fix declared; if the Blocking is still there, the batch ends `GAPS`. The verification of each finding, the contests, the round relays and the resumed audits are gone, and so are their lines in the report's `### Audit`.
  - `/cctoolkit:implement-tdd` no longer arms a question watcher: it launches the workflow and relays its report.
  - The `run-question` and `audit-round` commands, the question kinds of the work file and the question view of the `run-lot-pane` mod stay for now: `run-lot` no longer writes the lines they read.
- `cctoolkit`: the Bash hook forks only the guards a command can concern. Each guard's filter (a regex on the command or the agent type) is tested before its subshell, the batching nudge is skipped in a subagent, and the `graphify query` / `git grep` filter and the `rtk` normalisation no longer spawn `sed` and `grep` to find nothing. Measured on Windows (median of 11): `ls src` 1.25 s → 0.45 s on the main chain, 1.98 s → 0.80 s for the auditor; `git status` 2.04 s → 1.12 s; `cat README.md` 1.60 s → 0.84 s; `dotnet test` 1.19 s → 0.68 s.
- `cctoolkit`: the hooks that run after every tool leave before loading the kit's platform layer when the call is not theirs, and the run-notes hook reads the session and agent ids without `jq`. Measured on Windows: run-notes 0.25 s → 0.16 s on the main chain, 0.77 s → 0.41 s in a subagent; the knowledge reminder 0.28-0.33 s → 0.14-0.20 s in a subagent.
- `cctoolkit`: editing a file outside the use-case and test roots (a `README.md`, a doc, a domain file) no longer starts Python in the traceability and knowledge-base hooks. The roots are cached per repo (`cctoolkit config scope-cache`, rewritten by the hooks' own Python whenever `kit.config.json` or a preset changes); a file of a batch worktree, an unusual path or a stale cache still goes to Python. A repo without a knowledge base skips the reminder's Python on every edit. A `Read` carrying `offset` or `limit` leaves before any parse, and the size check forks once instead of six times. Measured on Windows: `README.md` edit — traceability 0.38 s → 0.16 s, knowledge reminder 0.78 s → 0.18 s; `Read` with `limit` 0.50 s → 0.20 s, a small file 0.68 s → 0.41 s.
- `cctoolkit`: the `run-plan` gate and the `run-lot` declaratives agent get the build command from `cctoolkit config command build` instead of reading `test-scope.md` (10 kB) to find it: one turn and about 2.5k tokens less per batch for each.
- `cctoolkit`: two batches run side by side (`run.parallelBatches: 2`) no longer compile at the same time during their TDD cycles. The test-project build of each RED and GREEN now waits under `cctoolkit build-lock`, like the solution builds and whole suites already did: on a measured project, overlapping builds took 39-45 min against 4-13 min alone.
- `cctoolkit`: `cctoolkit build-lock` takes its command as words after `--` (`cctoolkit build-lock -- <command> …`) instead of one quoted string run through `eval`; the old form is refused. The Bash guards and the `rtk` rewrite read the command again: a whole `IntegrationTests` run under the lock was out of the integration filter's sight. The `run-plan` preflight runs the build command literally instead of through `eval`.
- `cctoolkit`: `cctoolkit evals` runs the case files side by side (`-j N`, `EVALS_JOBS`, by default the CPU count up to 6) and times hooks with `$EPOCHREALTIME` instead of `perl`; a parallel run shows the latency table without failing on it, `-j 1` enforces it, as CI does. `--changed` runs only the case files your uncommitted changes reach, `--list` names them, `--profile` adds the slowest files and cases.
- `cctoolkit`: the `run-plan` gate relay runs at low effort like the other relays, and the cap of two parallel batches is read from one place.

## 2.5.1 — 2026-10-21

- `cctoolkit`: a test file the arbiter grants to a GREEN (`allow-test: <path>`) can now be edited. The TDD scope hook read the grant from the agent's first message, and inside a workflow that message is now the harness's relay of your request: every grant was refused, and the checks that read the RED prompt (`pendingRipple`, contract methods) were skipped. The hook now reads the prompt that follows the relay. A path ending the arbiter's sentence also kept its period (`MockGroupAccess.cs.`) and matched no file. Measured run: 4 GREEN attempts out of 10 refused a grant already given, until the batch was set aside.
- `cctoolkit`: a TDD agent writing through Bash after a `cd` is caught. `cd src/… && sed -i … Handler.cs` was judged from the repo root, so the relative path matched no root: the write was neither refused nor recorded, and a sibling agent running in parallel was blamed for it ("changed since RED start, I never touched them"). Paths after a `cd` are now read from its folder. Measured run: 3 attempts lost that way over two batches.

## 2.5.0 — 2026-10-21

- `cctoolkit`: `cctoolkit sheet-cycles --index` refuses a test method in two cycles, whatever their waves (a data-driven theory with one row per cycle never goes green alone: the runner filters a method, never a row), and a `full` test file shared by two cycles of successive waves, those under `layout.tests.shared` excepted — `run-lot` starts wave n+1's REDs beside wave n's GREENs, so the rows the next RED adds kept every GREEN red (seen on a run: three cycles of one permission theory, 3 and 4 GREEN attempts, two arbiters). `run-lot` now holds a wave back until the GREENs of the wave before when the two rewrite a test file, for a block validated by an earlier version or waves a resume makes adjacent; the index lists each cycle's `tests`.
- `cctoolkit`: the `run-lot` global green runs as two agents instead of one on the session model (measured on one batch: 9 min 53 s, 4 min 50 s of it the repair, the rest mechanical). `suites run`, on haiku, runs what the new `cctoolkit suites-plan <work> FX` resolves from the batch diff and the new `commands.suites` key of `kit.config.json`: the build, then each required suite in one message, with its `env` prefix and its integration filter. It reads no `test-scope.md` and fixes nothing. On a green first pass it records the closing level, and no other agent runs. `suites repair`, on the default model, opens only when a suite is red or a scope unresolved. It starts from the first pass's failures and output files, reruns the red suites filtered once and every suite once, and a retry relaunches the repair alone. A repo that sets no `commands.suites` (the `hexagonal` and `vertical-slices` presets) goes straight to the repair, which picks the suites as before.
- `cctoolkit`: test files written to reach the global green are now visible. The repair may write under the test roots only to promote an approved snapshot a sheet decision changes (quoting the line) or to edit a shared double under `layout.tests.shared` for a value the batch adds. Anything else is `BLOCKED`. Each write is declared in `testEdits`, and the run reads the tree back with `suites-plan --tests-changed`: an undeclared write is rejected. Every entry is listed under `## To validate` in the run report and handed to the audit as a point to verify. Measured run: a shared double edited and two received snapshots promoted, none of it in the report.
- `cctoolkit`: `/cctoolkit:plan-implementation` no longer waits for its inventory. The `Explore` starts in the background as soon as the gate passes, in the same message as `graphify explain`, `cctoolkit ask --id` and the reads of the spec, the rules, the template and the `Naming` / `Folder layout` tables. Its 60-line contract now also returns what the plan used to look for afterwards: the tests asserting a message, error code, route or response field the spec changes, with their methods; the callers of the aggregate methods it changes; how each handler's fixture builds it. Measured on a 6-batch plan: 6.4 min of inventory waited for in the foreground, then 7 min and about 25 searches by the main agent for what it did not return.
- `cctoolkit`: a `## Cycles` block no longer repeats its sheet. `elements`, `appliedIds`, `invariants`, `expectedCost` and `scenarios` are optional in `cctoolkit sheet-cycles`. Without them, the GREEN contract prints the `## Code elements` entries named after a file the cycle writes and the `## Design` table, and the RED contract says one scenario per method. A cycle sets them only to depart from the sheet, and `scenarios` only for what a method name cannot carry. Test names and paths stay required. A block written by an earlier version is still accepted as it is. Measured on 7 sheets: about 4 KB less per sheet (14 %). The example sheet moves to the `## Cycles` format.
- `cctoolkit`: the settings `/cctoolkit:kit-init` merges into your repo set `CLAUDE_CODE_RETRY_WATCHDOG=1`. Claude Code then retries a `429` or `529` (rate limited, overloaded) without end, where it used to give up after a few attempts. An autonomous `run-plan` or `run-lot` that hits a rate limit at night now waits instead of stopping, so you no longer lose hours to a relaunch. Press Esc to stop a retry in an interactive session. The key is added only if your settings do not set it yet: re-run `/cctoolkit:kit-init` to pull it.
- `cctoolkit`: the audit stops redoing what the gate already checked. The batch capture now opens with a `## Mechanical audit — F<n>` table (`Axis | Check | Result | Evidence`, each row `ok`, `gap` or `not checked`) holding the checks the script itself ran: `git diff --check`, files outside the batch, classified DDD/APP/PERF ids, closed cycles, the sheet's test methods found under the test roots, access cost, build and `ArchitectureTests`, green suites. `ddd-tdd-auditor` and `/cctoolkit:verify-ddd-tdd` read it first. They never re-check an `ok` row, turn a `gap` row into a finding, and judge only the `not checked` rows and the layer rules, so each audit round has fewer turns.
- `cctoolkit`: the Bash rewrite no longer approves a command in your place. When `rtk` answered nothing on a command the kit had rewritten (a `dotnet test` prefixed with `rtk`, a `/usr/bin/grep` stripped of its path), the module answered `allow` itself, so `dotnet test …; <anything>` ran without the prompt your permission rules would have shown. The rewrite now carries no decision, and your rules judge the rewritten command, as they judge rtk's own rewrites (`Bash(rtk *)` in the settings the kit merges). The path stripping only applies in command position (`ls -l /usr/bin/grep` is no longer turned into `ls -l grep`), and never inside a heredoc. A command running `git` in a linked worktree is left as written, because Claude Code's worktree isolation refuses `rtk git`. Without `rtk` on the PATH the module does nothing; before, it prefixed `dotnet test` with a missing command.
- `cctoolkit`: the `cat` bound now catches the dumps it missed. `cat big.md 2>&1`, `2>/dev/null` or `>&2` was taken for a redirect and passed, though the output still reaches the context. `sed -n '1,9999p'`, `sed -n '1,$p'`, a `sed` without `-n`, `awk 1` and `awk '{print $0}'` were not measured at all. They now count as the `cat`, `head` or `tail` they amount to. `sed -n 'A,Bp'` within the bound, `sed Nq`, `sed -i` and a pattern filter still pass.
- `cctoolkit`: `Agent(subagent_type: "fork")` is no longer refused for want of a model: a fork runs on the caller's model whatever the parameter.
- `cctoolkit`: inside a subagent, the one-batch-per-session guard of `/cctoolkit:implement-tdd` reads the agent's own transcript. The payload's `transcript_path` is the main conversation's there, so a subagent was refused because of a batch the main conversation had closed.
- `cctoolkit`: the `/clear` nudge speaks again after a `/compact`. A `/compact` keeps the session id, so the steps already crossed stayed silent for the rest of the session; a context back under a step now re-arms it.
- `cctoolkit`: `cctoolkit evals` no longer passes a case on an empty answer. A case whose `hook` does not exist fails. A case needing a tool (`rtk`, `ast-grep`) names it in `requires` and, without the tool, is skipped and counted apart (`N passed, M failed, K skipped`); `CCTOOLKIT_EVALS_STRICT=1`, set in CI, fails the run on a skip. The `decision` and `reason` of a Stop-style answer (`subagent-report-shape`) are now read, so the cases expecting a report to be sent back check that it is. `cctoolkit doctor --evals` shows a skip as a `WARN`. Each run writes its fixtures in a folder of its own (`evals/.fixtures/<run>/`): two runs at once no longer delete each other's files, which made dozens of cases fail at random.
- `cctoolkit`: `/run-plan` can run two independent batches at once. Set `run.parallelBatches` to 2 (`cctoolkit config parallel-batches`; default 1). The second batch runs in a worktree of its own under `.claude/worktrees/`, with builds and suites passing one at a time under a lock, then is gated, committed, rebased onto your branch and fast-forwarded. A conflict or a red build after landing undoes it and reruns it alone. The journal and the run report show which batches ran together. New `commands.worktreeSetup` key (`clean-architecture`: the `dotnet restore` a fresh worktree needs, builds running `--no-restore`).
- `cctoolkit`: new `cctoolkit batch-worktree` (`create`, `land`, `undo`, `remove`, `prune`) and `cctoolkit build-lock`; `suites-plan --lock`; `plan-next-batch --parallel [N]` (default 2, at most 2). `run-lot` takes optional `root`, `run`, `partner` and `lock` arguments; without them its prompts are unchanged.
- `cctoolkit`: the TDD scope, traceability, knowledge-read and auditor hooks follow a file into its batch worktree.

**Rules changed**: `rules/markdown-output.md` (the worktree Bash prefix joins the frozen literals). Re-run `/cctoolkit:kit-init` to pull it, the new `commands.worktreeSetup` default and `.claude/worktrees/` in the `.gitignore`.

## 2.4.0 — 2026-10-20

Faster batch closings, measured on a 5-cycle batch of 65 min, 45 of them spent closing (pre-audit, audit, fix, re-audit).

- `cctoolkit`: a RED that finds its tests already green (`ALREADY_GREEN`) no longer skips a GREEN that still has files to write. The RED reports as `pendingRipple` the files of the cycle's signature ripple and creations that the batch has not changed (`cctoolkit sheet-cycles <sheet> --cycle <id> --pending <work file>`); the TDD scope hook checks that list against the tree, and run-lot runs the GREEN on those files. The list is kept in the cycle's line of `run/.work.jsonl`. Before this, a resumed cycle whose 9 handlers were never touched passed the suites and was only caught by the audit: a 15 min fix outside TDD, then a second audit. Expected gain: about 20 min on such a batch.
- `cctoolkit`: the TDD scope hook refuses a write made from code an interpreter reads in a heredoc (`python - <<'E' … open(p, 'w')`), wherever it points. Such writes escaped the per-agent log, so a parallel RED was blamed for a GREEN's handlers and stopped (arbiter, then a new RED: about 2 min 30). The TDD agents write through Edit and Write.
- `cctoolkit`: `cctoolkit pre-audit` gate 4 fails an unbound test only when the batch adds it. An older test in a class the batch touches is listed with `·`. When the repo git-ignores its rule sheets (`layout.ruleSheet`), the trait check is listed and never fails, and the closing never recreates those files. Before this, a pre-audit agent spent 8 min recreating 9 git-ignored handler `CLAUDE.md` files from history, then a second pre-audit ran (4 min).
- `cctoolkit`: the agent that fixes an audit's findings gets, for each cycle, its id, its behaviour, the files it wrote, and the command that prints its ripple and elements. It edits with Edit and Write, never through a Bash script. Before this, it spent 8 min 30 re-reading what the batch sheet already held. Expected gain: about 5 min per fix round.
- `cctoolkit` `run-lot`: a batch closes `full` or `light`, decided on its files, not by the model. `cctoolkit closing-level <sheet> <work>` reads the batch diff once the suites are green: `full` when a file matches a `closing.full` rule of `kit.config.json` (authorisation, permission, security, migration on any change; a public contract or an approved snapshot modified or deleted — the defaults are in each preset), more than `closing.maxProductionFiles` production files (12), a cycle with a `ripple`, or `"closing": "full"` in the sheet's `## Cycles` block; `light` otherwise. `"closing": "light"` in the block lifts the production cap and the ripple criterion, never an authorisation, migration or contract rule: such a batch closes full, the refused request named. `light` keeps the suites and the pre-audit, then one review of the diff limited to Correctness and Scope (no audit capture, no verification agent per finding); a fix round runs the suites again instead of a second review, and a second review follows only a Blocking. The next sheet is reviewed only when it names a type the batch modified or deleted. The level and its reasons go to a `closing` line of `run/.work.jsonl` and to a `Closing:` line of the batch report. Expected gain on a light batch: about 6 min (a 6 min audit becomes a 2 to 3 min review, no next-batch review nor sheet amendment).
- `cctoolkit` `run-lot`: on a batch the `## Cycles` block plans light (`sheet-cycles --index` now prints that level, and each cycle's code files), one new `tdd-cycle` agent writes a cycle's RED then its GREEN. The TDD scope hook keeps both roles apart on the tree: the agent is a test author until its RED checkpoint, `cctoolkit tdd-scope red`, which runs the RED checks (source files beyond the stubs, the filtered command rerun, failures on the stub, the contract's methods, a RED that passes at once), then snapshots the tree; from there it is an implementer, test files read-only, and its output must carry the checkpointed RED unchanged. A RED or GREEN the workflow rejects goes on through the usual agents, arbiter and retries. Cycles of one wave run side by side only when their files are disjoint. Expected gain: 30 to 60 s per cycle (one spawn and one contract load less, no second read of the files the RED opened).
- `cctoolkit`: new `commands.testFast`, what RED and GREEN run: the suite's test project built alone, then its test assembly run directly — `clean-architecture` preset: `rtk dotnet build tests/<P>/<P>.csproj --no-restore && dotnet tests/<P>/bin/Debug/net*/<P>.dll`, the runner's filter appended. Unset, it is `commands.build && commands.test`. The solution build and whole suites stay with the global green and the audit. The TDD scope hook reruns this command for its RED check; the IntegrationTests guard refuses an unfiltered assembly run as it refuses an unfiltered `dotnet test`; `cctoolkit doctor` warns on a project path that does not exist or an assembly glob matching several files.
