# Changelog

One section per release, newest first, headed `## <version> — <date>`: `cctoolkit` and its mods share one version since 1.6.0, each entry names the plugin it changes. Older sections, headed `## <plugin> <version>`, date from per-plugin versions.

A release that changes a file under `rules/` or `presets/*/rules/` lists it under **Rules changed**, one under `presets/*/skills/` under **Skills changed**: those files are copied into your repo, so you pull them by re-running `/cctoolkit:kit-init`, which shows each difference and asks.

## 1.12.0 — 2026-10-15

- `cctoolkit`: what the RED and GREEN agents wrote is checked on the tree, no longer on their report. A new hook, `tdd-scope-guard.sh`, snapshots the source and test roots when each TDD agent starts; the implementer's `Edit`/`Write` of a test file is denied unless the arbiter granted it or it is a `.verified.txt`; a write through Bash under those roots (redirection, `sed -i`, `rm`, `git checkout`, a formatter…) is denied to both agents. When an agent returns, the tree since its snapshot, minus what agents running beside it wrote, must match: no test file changed at GREEN unless granted, no source file changed at RED outside its `stubs`. The agent puts a file back with `cctoolkit tdd-scope restore`, or returns `BLOCKED` with the hook's exact reason, which `run-lot` hands to the retry and the arbiter. `testsDiff` and `productionDiff` stay in the reports for display only.
- `cctoolkit`: a RED must fail on its assertion. The hook reruns the RED's test command itself and refuses, by name, a test failing on the stub's `NotImplementedException` (new `tdd` keys of the presets: `failedTest`, `stubFailure`, `stubLogic`; a repo that keeps its own copy of a preset adds them to turn the check on). A stub whose added lines look like logic is listed in the audit capture for the auditor to judge.
- `cctoolkit`: audit findings carry a `Closure`, the observable state that closes them; `Expected fix` is a suggestion. The audit fix may contest a finding only by naming a concrete harm; the resume audit answers each contest Accept, Counter, Refute or Escalate (`/verify-ddd-tdd` § Contested findings). Accepted and escalated findings go to `## To validate`, never hold the batch.
- `cctoolkit`: the resume audit reads the files the fix actually changed, read off the tree by the new `cctoolkit audit-round`, no longer the list the fix declared. A file the fix changed that no finding cites becomes a Scope Major. Each round is recorded in `run/.work.jsonl`; findings that do not go down while the change set grows stop the rounds.
- `cctoolkit`: `run-plan` checks, from the second batch set aside, whether the batches set aside share a cause (same spec ambiguity, wrong assumption, workaround). A shared cause stops the plan: the run report opens `## Plan stopped — common cause` with what to fix before relaunching. Distinct causes leave the plan going.
- `cctoolkit`: `run-plan` stops cleanly between two batches when a pause is asked from `run-lot-pane` (`paused by user`). Notes attached to a batch in the pane reach its agents (`cctoolkit run-notes`); answers given in the pane to `## To validate` are written into the sheet by `cctoolkit run-validate`, run at the start of every `run-plan` and `run-lot`.
- `run-lot-pane`: the pane steers the run, through the run's files only. `v` lists what the run decided without you (`## To validate` of the reports, divergences, the breaker's stop, notes taken): `✓ keep`, `✗ reject` or `✎ amend` with a text, applied to the sheet at the next run start, or at once with the `cctoolkit run-validate apply` line the view shows; the relaunch command appears once applied. `z` asks `run-plan` for a pause between two batches, `n` attaches a note to a batch. A banner on every view and above the prompt counts down a pending question to the moment its recommendation applies. The Audit phase shows its rounds (`R1 findings 3 → 2 · files 4`, contests and their answer, a diverging round in red), an agent its rejected attempts with their reason, and `g` on the plan draws the dependency graph, set-aside batches and the batches they hold back in red. Keys are lower case: the mod API takes no capital letter.

**Rules changed**

- `rules/markdown-output.md`: new frozen literals — the GREEN grant line and the hook's reasons (`tests modified at GREEN:`, `RED on stub:`), the `Closure` column of a GAPS verdict and the contest answers, `## Plan stopped — common cause`, the work-file kinds `audit-round`, `attempt`, `breaker`, `ack`, the pane file `run/.pane.jsonl` and `PAUSED`.

## 1.11.0 — 2026-10-15

- `cctoolkit`: `/quality-report` runs as a workflow, `run-audit`, in a throwaway worktree of the main branch: your checkout is never touched, uncommitted work never enters a report, and an audit can run beside a `run-lot`. The skill only asks the Stryker mode and launches it; the run asks nothing more, a tool that fails reads `missing` and the run goes on. Stryker is **off by default**: the report says `Skipped`, a fourth evidence status shown `—` in the summary and named among the blind spots; `Full` and `Since` stay available, Stryker starting only once every measure reading the sources is done, stopped past 4 h (1 h 30 in since), its reports kept per commit and reread on a rerun. Each agent writes its own fragment and `cctoolkit report-assemble` merges them: no figure is copied by a model, `tests.total` is summed, an unknown first-level key is refused. The report agent runs on Opus, the measuring ones on Sonnet or Haiku. Followed in `run-lot-pane` like any workflow.
- `cctoolkit`: the report gains four measures, each `{status, reason, commit}` under `codebase`, all from the new `cctoolkit audit-collect`: rule traceability (`rules-coverage` and `untagged-tests`, both with a new `--json`) in §3; suppressions (`#pragma warning disable`, `SuppressMessage`, `NOSONAR`, `eslint-disable`, `@ts-ignore`, `ReSharper disable`), dependency vulnerabilities (`dotnet list package --vulnerable --include-transitive`, `npm audit`; without network, `missing`) and Infrastructure calls in loops (`access-cost --all --json`, C# only) in §6, now `Static quality`. §7 opens on the Danger Zone × coverage × survivors table of the new `cctoolkit risk-cross`; §8 actions name the skill that carries them.
- `cctoolkit`: new commands `cctoolkit bg` (detached job, bounded `wait`: what outlasts a 10-min Bash call, Stryker and SonarQube, no more `nohup` + Monitor), `cctoolkit audit-worktree`, `cctoolkit audit-collect`, `cctoolkit risk-cross`, `cctoolkit report-assemble`. `cctoolkit quality-report-check` checks the `skipped` status and the `codebase.*` blocks.

**Rules changed**

- `rules/markdown-output.md`: the evidence statuses (`skipped` added) and `report-assemble` join the quality report's frozen literals.

## 1.10.0 — 2026-10-15

- `cctoolkit`: `/quality-report` ranks the hotspots, the files both complex and often changed, after Michael Feathers' churn-versus-complexity map. New `cctoolkit hotspots`: churn over the main branch's history with renames followed, the commit creating a file, pure renames, merges and `.git-blame-ignore-revs` left out; cyclomatic complexity per function by lizard (`pip install lizard`), read at the analysed commit; files split in Danger Zone, Cowboy Code, Fertile Ground and Healthy Closure at the median. Ranked on the last 365 days before the report commit (`--days`), the whole history counted beside it: churn that stopped years ago is no hotspot. `fix:` commits are counted per file, so a bug nest stands out from a busy file. A second table ranks on the worst function, catching a short file with one monster function that the total misses. Step 8 checks two listed files by hand against `git log --follow` and lizard. The report gets a §2 `Hotspots` subsection, every Danger Zone file goes to §7 or is explained, and the JSON an optional `activity.hotspots`. Without lizard the hotspots read `Missing`: no file is ranked on churn alone.
- `cctoolkit`: `/quality-report` no longer lets a missing result pass for a clean one. Each block is `measured`, `not_configured` or `missing` (`metadata.evidence`, with `metadata.commit`): a run that failed, timed out or belongs to another commit is `Missing — <reason>`, 🔴 in the summary, `null` in the JSON, never `0` nor last month's figure. A CI result counts only when the run's head SHA is the report commit. `cctoolkit quality-report-check` checks it; an older report without `metadata.evidence` gets a warning.
- `cctoolkit`: `/learn` also reads the `## Audit gaps` of the `run-lot` reports, `todo/<code>/run/batches/FX.md`. Those stay in the repo, where Claude Code removes transcripts after `cleanupPeriodDays` (30 days by default): an audit gap older than that was lost to `/learn`. A gap found both in a report and in a transcript counts once.
- `cctoolkit`: the report's conclusion gets `What the measures cannot see`: missing evidence, `since`-mode Stryker, issues hidden by suppressions, migration churn, moved code.

## 1.9.4 — 2026-10-14

- `cctoolkit`: the batch audit of `run-lot` is faster. Measured on a 27-cycle batch: 24 min of audit, 60 % of it lost.
  - `ddd-tdd-auditor` runs at effort `medium` with 70 turns instead of `high` with 45: the first auditor ran out of turns without a verdict.
  - Each auditor appends its findings to a notes file as it goes; the second attempt after an auditor without result starts from those notes instead of redoing the audit.
  - Past 12 cycles, one capture feeds two auditors in parallel: code axes (Correctness, Reuse, Simplification, Cost, Placement, Comments) and plan axes (coverage, Test, Plan, Scope, validations). Their verdicts are merged.
  - New Bash guard for the auditor only: no background command, no recursive `grep` (use `git grep`), no rerun of a suite the global green ran green while no source or test file changed since. `cctoolkit audit-capture` takes `--suites-green` to record those suites.
- `cctoolkit`: a batch whose cycles each add an entry to one registry file no longer runs wave by wave. Registry entries (code constant, catalogue entry, enum member) join the declarative artefacts written once before the first RED; `cctoolkit sheet-cycles --index` refuses a production file in more than 3 cycles and says to move those entries. Measured on a 29-cycle batch: 23 cycles sharing one error-code file gave 27 waves of one cycle, 19 min of RED in sequence. An existing sheet the rule now refuses is redesigned by the run.

Everything decided without the user is marked `user decision to validate` (`user decision` once the user answers) and listed in `## To validate` of the batch report (renamed from `## To review`), gathered by run-plan into `TO-VALIDATE.md`, to read after the plan.
